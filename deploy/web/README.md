# Единый вход OG

Локальный адрес: `http://localhost:8080`. Nginx разделяет маршруты:

- `/api/v1/` → Gateway. Ошибки API не заменяются SPA HTML; proxy не повторяет POST.
- `/admin/` → Django с его собственной staff-сессией.
- `/static/` → volume, заполненный one-shot `collectstatic`, read-only в proxy.
- `/internal/` → `404`, private API не доступен через web.
- остальные адреса → frontend, deep links возвращают `index.html`.

`nginx.dev.conf` вместо static frontend проксирует Vite с WebSocket HMR.
Common forwarded headers находятся в `proxy-headers.conf`: клиентские значения
заменяются, не добавляются к доверенным. `Host` проверяется whitelist Nginx
(`localhost`, `127.0.0.1`) и Django. Service token остаётся серверным.

## Файлы домашних заданий

Только `/api/v1/homework/<id>/files/<id>` допускает тело до11МиБ: один файл
до10МиБ плюс multipart. Остальной API сохраняет предел1МиБ. Gateway и Homework
независимо считают реальные байты, в том числе без Content-Length, принимают
только одну часть `file` и закрывают временный spool после запроса.

Nginx: ожидание входных данных300с, соединение с Gateway5с, отправка120с,
ожидание ответа300с. Это таймауты простоя между операциями, не обещание общей
длительности; parser каждого приложения дополнительно ограничен300с.
Внутренний файловый HTTP-клиент: connect/pool5с, read/write120с; JSON остаётся5с.
Proxy не повторяет файловый PUT автоматически: при потере ответа браузер сможет
повторить тот же file_id и получить уже подтверждённую версию.

Локальная проверка конфигов и реальных лимитов в одноразовых Docker-контейнерах:
`OG_TEST_UPLOAD_PROXY=1 python3 -m unittest discover -s deploy -p test_homework_upload_proxy.py -v`.
Рабочий Compose, env-файлы и volumes этим тестом не используются.

## Сборка и окружение

Frontend image: Node 24.19.0/pnpm 11.25.0 только на этапе сборки; в финальном
image Nginx 1.30.5 и static files. Входной web image — отдельный Nginx.
Фиксированные версии и lock обеспечивают повторяемость; перед обновлениями
проверяйте peer requirements, тесты и security advisories.

Все диагностические ports базового Compose привязаны к loopback. Override
`compose.production.yaml` сбрасывает их через `!reset []`, отключает source
mounts Backoffice и использует Gunicorn. Единственный host port — web 8080,
тоже loopback. Требуется Compose с `!reset`/`!override` (проверено CLI 5.5.1).
Не выставляйте upstream services напрямую: сейчас их защита предполагает Gateway.

MinIO и `mc` временно берутся из сторонних зеркал с закреплёнными SHA-256:
исходные старые образы больше не удалось получить из прежних реестров. Образ
MinIO совпадает с ранее использованным manifest digest; у `mc` сверены слои и
конфигурация с прежним образом. Зеркала могут стать недоступными, а закрепление
не исправляет уязвимости старых версий. Перед публичным использованием нужна
отдельная проверка безопасности и выбор поддерживаемого S3-хранилища.

### Ручная копия PostgreSQL

`python3 tools/backup_postgres.py /var/backups/og-postgres-YYYYMMDD-HHMM`
создаёт новую папку с правами только для владельца и отдельный `pg_dump`
каждой из девяти PostgreSQL-баз. Существующая папка не перезаписывается;
`COMPLETE` появляется, только если все команды успешно завершились и файлы
начинаются с заголовка PostgreSQL. При ошибке останется неполная папка без
маркера; её нельзя использовать как завершённую копию.

Это не полная резервная копия платформы: архивы не включают ClickHouse, файлы
MinIO, конфигурацию, роли PostgreSQL и брокер Kafka. Снимки разных баз сделаны
в разные моменты и не являются единой согласованной точкой восстановления.
Копия на том же диске не защищает от потери VPS. Внешнее зашифрованное
хранилище, автоматизация, срок хранения и проверка восстановления всей системы
должны быть настроены отдельно. Дампы могут содержать личные данные и секреты.

### Ручная копия ClickHouse

`python3 tools/backup_clickhouse.py og-YYYYMMDD-HHMM` создаёт архив базы
`default` штатной командой `BACKUP DATABASE` в ClickHouse volume. Имя должно
быть новым и состоять только из латинских букв, цифр, дефиса и подчёркивания.
Подтверждается статус `BACKUP_CREATED`; копия остаётся на диске VPS и не
включает PostgreSQL, MinIO, env-файлы и Kafka. Внешнее защищённое хранение,
регулярное расписание и восстановление вместе с остальными данными нужны
отдельно. Команда предполагает доступный `clickhouse-client` в контейнере.

## Перед публичным размещением

Эта конфигурация **не является завершённым HTTPS deployment**:

1. Повторно проверить Gateway auth/Origin/logout, единый вход и admin-only
   upstream routes в итоговом окружении; отдельный вход Django остаётся резервным.
2. Настроить TLS на доверенном ingress и конкретный публичный hostname в Nginx,
   убрать generic/default-host доступ. Не доверять forwarded headers из Интернета.
3. Настроить Gateway `PUBLIC_ORIGIN=https://...` и
   `REFRESH_COOKIE_SECURE=True`; добавить тот же origin в Django trusted origins,
   hostname в allowed hosts и `BACKOFFICE_SECURE_COOKIES=True`.
4. Если TLS завершается на ingress, изменить **доверенную цепочку proxy**:
   текущий local Nginx всегда передаёт свой `$scheme` (HTTP). Нельзя просто
   включить `BACKOFFICE_TRUST_PROXY=True` и ожидать HTTPS — ingress должен быть
   единственным сетевым источником, а Nginx должен выставлять проверенное `https`.
5. Отдельно проверить Host/CSRF/Secure-cookie, DB/backups, журналирование без
   токенов, ограничения ресурсов и healthchecks. Только затем публиковать web.

Не добавляйте `VITE_*` с паролями/токенами: они могут попасть в browser bundle.
Не делайте `docker compose down -v` ради смены режима — данные должны сохраняться.

### Ограничение попыток входа

Nginx отдельно ограничивает запросы к `/api/v1/auth/login` и `/admin/login/`
по IP: 2 запроса в секунду с кратковременным запасом до 10; превышение даёт 429.
Это защита от частых запросов с одного адреса, а не от распределённого перебора.
Она действует только для трафика через Nginx: напрямую опубликованные локальные
порты API её обходят. За внешним ingress без доверенной настройки реального IP
все пользователи могут выглядеть как один адрес. Перед публикацией нужно закрыть
прямые порты и безопасно настроить цепочку доверенных прокси и ограничения там.

## Общий аудит и успеваемость

Суперпользователь Django открывает `/admin/analytics/`; административная страница
портала `/analytics` пока тоже доступна. В локальном демо аккаунт Gateway
`admin@demo.og.test` явно связан с Django `root`. После входа в портал ссылка
открывает админку без повторного пароля. Права Django при этом проверяются отдельно;
отдельный Django-вход сохранён как резервный и не является общим входом.
Локальная демонстрационная учётка портала:
`admin@demo.og.test`, пароль `DemoSchool2026!` — только локальная среда: демо-админ
не входит в публичный демо-доступ, на сервере у него отдельный непубличный пароль.
Витринные демо-учётки (учитель/ученик/родитель) и их пароль публичны: сайт —
портфолио, демо-вход на `/login` выполняется одной кнопкой.

Старый refresh-токен без ID общей сессии при обновлении заменяется новым токеном
с ID сессии. При выходе из админки её Gateway-сессия
отзывается, а открытая вкладка портала узнаёт об этом при следующем запросе.
Для проверки новых общих сессий и обоих направлений выхода доступна команда
`poetry -C services/gateway run python ../../tools/verify_unified_auth.py`.

На новой базе связь создаётся явной командой после создания пользователя Gateway
и сотрудника Django. Сначала найдите UUID нужного администратора, например:

```bash
docker compose exec gateway-postgres psql -U gateway -d gateway -c \
  "SELECT id, email, role, is_active FROM users WHERE email = 'admin@demo.og.test';"
docker compose exec backoffice-api poetry run python manage.py \
  link_gateway_identity root UUID_ИЗ_ВЫВОДА
```

Команда не создаёт аккаунты и не заменяет существующую связь. Перед её запуском
проверьте, что связываете действительно одного сотрудника: она может дать
указанному пользователю Gateway права связанной учётной записи Django. Вход
дополнительно проверяет роль администратора Gateway и права сотрудника Django.

События проверки ДЗ, состава класса, расписания, регистрации/входа и результатов
действий Backoffice доставляются через Kafka в ClickHouse. Source-сервисы сначала
сохраняют outbox в своей транзакции; relay отмечает отправку после ответа Kafka.
Повторная доставка одного event_id не увеличивает число оценок в отчёте.
Старые оценки автоматически не переносятся: пустой отчёт после первого запуска
не означает потерю существующих работ. Нужна новая проверка после подключения аудита.

Новые процессы: `analytics-audit-migrations`, `analytics-audit-worker`,
`homework-outbox-relay`, `journal-outbox-relay`, `gateway-outbox-relay`,
`backoffice-outbox-relay`; расписание использует `schedule-outbox-relay`.
`analytics-worker` остаётся отдельным потребителем старого отчёта нагрузки.
При запуске `analytics-audit-migrations` создаёт также UUID-таблицы снимков
уроков и расчёта нагрузки. Старые таблицы не меняются и их история автоматически
не переносится: для переноса старых числовых ID нужны подтверждённые соответствия.
Секрет чтения `ANALYTICS_READ_SERVICE_TOKEN` Gateway должен совпадать с
`GATEWAY_READ_SERVICE_TOKEN` Analytics; это не JWT и не публичная переменная Vite.

## Симулятор умной ручки

Откройте урок в личном расписании → «Умная ручка». Ученик рисует мышью/пальцем,
свой преподаватель выбирает ученика по имени и видит страницу только для чтения.
Родитель и администратор не получают рукописную историю через этот маршрут.
Для демонстрации войдите учеником `student01.1@demo.og.test` и преподавателем
`teacher01@demo.og.test` в разных профилях браузера (урок1).

Дополнительный запуск: `docker compose -f compose.yaml -f compose.dev.yaml up --build -d pen-api gateway-api web`.
Pen имеет свою БД/добавочную миграцию; прямого публичного порта нет.
`PEN_SERVICE_TOKEN` Gateway совпадает с `GATEWAY_SERVICE_TOKEN` Pen.
История хранится в PostgreSQL; подтверждение пачки отправляется после commit.
Сеть может доставить запрос повторно — batch_id оставляет одну запись.
Пока неподтверждённые точки находятся только в памяти вкладки: не закрывайте её
при надписи «Сохраняем штрихи». Лимит20000точек/4096пачек на страницу.

WebSocket идёт через Gateway, JWT — в первом сообщении, не URL. Владельцы
проверяются перед записью и минимум каждые5с открытого соединения. Изменение
класса закрывает доступ, но мгновенного распределённого отзыва не обещается.
Преподаватель догружает сохранённые пачки каждые0.5с. Это минимальный симулятор,
не рассчитанный на высоконагруженный поток настоящих устройств.

`poetry -C services/gateway run python ../../tools/verify_pen.py` проверяет
настоящие WS ученика/учителя, повтор ACK и восстановление истории. Скрипт
добавляет один идемпотентный демо-штрих, ничего не очищает и отзывает свои сессии.

## Тестовая оплата обучения

Ученик и связанный родитель открывают `/billing`. Суперпользователь Django
использует `/admin/payments/`: там доступны история, полный возврат и ручная
сверка. Прежний `/billing` для администратора портала сохранён для совместимости.
Ученик/родитель выбирает месяц, сумма задаётся Billing и сохраняется в заказе.
Учителю финансовые данные недоступны. Неоплаченная четверть может ограничить
ученику доступ к занятиям и учебным материалам, не отключая вход и оплату.
Ограничение включается настройкой `ENFORCE_TUITION_ACCESS=true` в Gateway и по
умолчанию выключено: без тестового магазина пользователи не смогут оплатить.
В текущем демо четверти начинаются 1 сентября, 1 ноября, 1 января и 1 апреля,
в июне–августе учебного периода нет. Дата определяется по Москве. Отсутствие
оплаченного четвертного счёта после начала периода считается неоплатой;
месячный платёж не становится оплатой четверти. Ученик без класса не считается
должником. Сбой Journal или Billing даёт 503, а не сообщение о долге.
Процесс `billing-invoices` раз в час читает текущий состав классов Journal и
заранее создаёт неоплаченные счета за текущую и следующую четверти. Повторный
запуск не создаёт дубликаты и не меняет сумму имеющегося счёта. Для перехода на
следующий учебный год счета появятся после назначения ученика в класс этого года.
Отдельный `BILLING_READ_SERVICE_TOKEN` в Journal должен совпадать с
`JOURNAL_SERVICE_TOKEN` в `services/billing/.worker.env`; он даёт Billing только
чтение классов, не права на их изменение. Смена токена требует обновить оба файла.
Отдельных напоминаний о приближении срока пока нет. Перед включением ограничения
нужно решить, как учитывать уже оплаченные месячные счета: они автоматически не
преобразуются в квартальные.

Возврат и сверка в Backoffice требуют повторного подтверждения отдельной учётной
записью администратора Gateway. Пароль и access-токен не сохраняются в Django;
временный refresh-токен отзывается. В журнал Backoffice попадают Django-сотрудник,
UUID администратора Gateway и ID платежа, но не пароль или токен. При потере
ответа повтор теми же двумя учётными записями использует прежний ключ возврата.
Принятие запроса ещё не означает, что ЮKassa завершила возврат.

При обновлении существующего развёртывания сначала обновите
`analytics-audit-worker`, а уже затем `backoffice-api`: новые события платежей
содержат ID платежа, который старый обработчик аудита не распознаёт. При первом
запуске новой системы старого обработчика нет.

Запуск локальных процессов:

```bash
docker compose up -d --build billing-api billing-reconcile
docker compose up -d --build analytics-api analytics-audit-worker
docker compose up -d --build billing-outbox-relay
docker compose up -d --build gateway-api frontend web
```

Для первого запуска нужны согласованные `.env`, `.postgres.env`, `.worker.env`
из примеров в `services/billing/`. Пароль PostgreSQL должен совпасть с паролем
в `DATABASE_URL`. `GATEWAY_SERVICE_TOKEN` Billing совпадает с
`BILLING_SERVICE_TOKEN` Gateway; `BILLING_BASE_URL=http://billing-api:8000`.
В текущем локальном окружении эти пары уже заполнены. Повторно их генерировать
не требуется. Существующий пароль БД нельзя просто заменить в env без смены
пароля PostgreSQL: заполненный volume не инициализируется заново.

Ключи `YOOKASSA_SHOP_ID` и `YOOKASSA_SECRET_KEY` намеренно пустые. Указывать
только данные **тестового** магазина в `services/billing/.env`, не в Git/чат.
Затем пересоздать `billing-api` и `billing-reconcile`. Боевой магазин код
отклоняет после `GET /v3/me`; каждый ответ платежа дополнительно проверяется.
Цена демо: `QUARTER_PRICE_KOPECKS=900000` (9000 ₽ за четверть); прежняя
`TUITION_PRICE_KOPECKS=300000` относится к месячным счетам. Суммы задаёт сервер.

Повтор после неизвестного ответа использует прежний ключ и прежнюю попытку.
Вернувшись из ЮKassa, нажать «Проверить статус в ЮKassa»; отдельный процесс
также сверяет ожидающие попытки каждые30с. Переход по return URL не означает
успешную оплату. После23ч неизвестный POST не повторяется: нужна ручная сверка
admin с ID из кабинета. Полный возврат требует отдельного подтверждения admin.
Частичные возвраты, подписки и фискализация не реализованы.

Публичный webhook: `/api/v1/billing/yookassa/webhook`. Для регистрации в ЮKassa
нужен будущий внешний HTTPS-адрес; localhost из интернета не доступен.
Локально достаточно сверки по кнопке/worker. Webhook не доверяет присланному
статусу: используется собственный GET к провайдеру. Неизвестный ID игнорируется.
Аудит оплаты/отмены/возврата записывается вместе с состоянием в outbox и
доставляется через Kafka в общий ClickHouse-журнал.

Без пользовательских тестовых ключей выполнены проверки на изолированной PG,
HTTP MockTransport, настоящих Kafka/ClickHouse, Nginx и браузерах Chromium/Firefox.
Настоящий checkout в тестовом магазине ещё **не проверен**.
Официальная документация: [тестовый магазин](https://yookassa.ru/developers/payment-acceptance/testing-and-going-live/testing),
[уведомления](https://yookassa.ru/developers/using-api/webhooks),
[идемпотентность](https://yookassa.ru/developers/using-api/interaction-format).

## Учебные документы

Администратор открывает `/documents`, выбирает справку, договор, акт или квитанцию.
Для акта нужен период до366 дней. Для квитанции вводится только номер платежа:
Gateway проверяет подтверждённую тестовую оплату и сам получает ФИО, месяц и
сумму. Ручную подмену суммы API отклоняет. Без ключей ЮKassa полный сценарий
настоящего тестового платежа и его квитанции ещё не проверен; PDF-шаблон и
проверки контракта проверены отдельно.

Публичные запросы идут через JWT Gateway. Documents проверяет отдельный Bearer
и UUID создателя из служебного заголовка. Знание UUID чужого задания не даёт
доступа к статусу/PDF. Прямой прежний `/documents` на8002 тоже закрыт служебным
токеном. Исторические задания без автора сохранены вБД, но портал их не выдаёт.

Job и намерение отправить задачу Celery сохраняются вместе. Dispatcher отправляет
задачу вRabbitMQ, worker строит PDF и сохраняет его вMinIO, затем отмечает
задание готовым. Повтор создания с тем же ключом возвращает прежнее задание;
поздняя ошибка не откатывает готовый документ. Kafka-outbox готовности/ошибки
отделён от Celery task-outbox и не содержит ФИО или текста документа.

## Личные уведомления

Страница `/notifications` доступна всем активным ролям. Она показывает только
свои сообщения и счётчик, обновляет их каждые30с при открытой странице.
Прочтение проверяет адресата атомарнымUPDATE; повтор сохраняет первое время.
Уведомление не предоставляет доступа к целевому ДЗ/документу, если его владелец
уже запретил доступ. Внешних email/SMS/push нет.

Notifications слушает `platform.events.v1` отдельной группой`notifications-v1`:
проверка ДЗ уведомляет ученика; оплата/отмена/возврат - ученика и плательщика;
готовность/ошибка PDF - создателя задания. Совпавший ученик-плательщик получает
одну запись. Inbox-маркер и получатели записываются одной транзакцией в своейPG.
Повтор Kafka не удваивает сообщения. SQL/Kafka-сбой завершает worker; при
перезапуске он читает с последнего подтверждённогоoffset. Некорректный целевой
пакет идёт в`notifications.dlq` только сhash/исходнымoffset, без сырогоJSON/ФИО.

```bash
docker compose up -d --build notifications-api notifications-worker
docker compose up -d --build gateway-api frontend web
```

Своя БД, миграция010291a6951b, секреты в`services/notifications/.env` и
`.postgres.env`, Kafka-настройки в`.worker.env`. Gateway использует
`NOTIFICATIONS_BASE_URL=http://notifications-api:8000` и свой
`NOTIFICATIONS_SERVICE_TOKEN`, совпадающий с`GATEWAY_SERVICE_TOKEN` Notifications.
Локальные значения уже согласованы. Сервис не публикует порт БД/API наружу.
